# Tabbyfin: Roadmap

What's missing and what still needs work, as of 2026-10-15. Done items are marked ✅ and kept for context.

- **Egui:** the app runs on egui/eframe, drawn with wgpu, with mpv's frames imported into wgpu (§7). `docs/PLAN.md` §2–§6 describe what was built.
- **Egui branch: accepted differences** (X3's sweep, 2026-10-28; the restyle landed in R7). The egui app matches `main`'s features and look: R1 brought the colours, radii, spacing and text styles, R2 the animations, R3 the mascot loader, R4 the search box's motion, R6 the player's overlay and R7 the last layout details (the centred sign-in form, Home's shelf padding, left-aligned card titles) and the search box's clear button. The sign-in screen has moved on from `main`'s (2026-10-29): one panel under the mascot, which watches the fields as they're typed in, shuts its eyes for the password and looks confused over an error, with a title per step instead of `main`'s "Tabbyfin" header. Since 2026-10-29 it's also the first screen in the cozy look the whole app is moving to (`docs/PLAN.md`): a lavender backdrop and glow, a raised panel, lavender main buttons, and saved accounts as avatar rows; the restoring screen shares the backdrop. The list menus share one popup menu (`widgets/popup.rs`, 2026-10-29), which the keyboard walks once open; what's accepted for now: the item menu opens with a right-click only, the player's settings and chapters menus take the pointer only; selects (`widgets/select.rs`) open the same popup menu, from the keyboard too in Settings, where Left/Right also step them; Tab passes the top bar's buttons before the page. In WSL debug builds it idles at 0 % CPU (`main` ~0.8 %), plays software video at about 60 % of `main`'s CPU, and holds about half of `main`'s memory on a 10,000-item library.
- `docs/PLAN.md` describes the architecture, and `docs/in-app-video.md` the video pipeline. This document only lists gaps.
- **Priority:**
  - **P1:** needed before calling it v1.
  - **P2:** expected by most users soon after.
  - **P3:** nice to have, or a later scope.
- **Effort:**
  - **S:** under a day.
  - **M:** a few days.
  - **L:** a week or more, or blocked on hardware we don't have.

## Where things stand

v1 scope is mostly done:
- **Sign-in:** password and Quick Connect, with the session kept between launches.
- **Browsing:** Home shelves, library grids, and series, season, episode and movie pages, all with images and a disk image cache.
- **Search** and **mark as watched**.
- **Playback inside the window:** libmpv with GPU texture sharing on Windows and Linux, and zero-copy decoding on Windows through ANGLE.
- **Server reporting:** start, progress and stop.
- **Player controls:** tracks, versions, volume, next episode and autoplay.
- **CI:** builds packages for all four targets.
- **UI:** egui/eframe on wgpu, with the player's GPU frames imported into wgpu on Linux and Windows (§7).

The big gaps:
- **Release hygiene:** a signed macOS build.
- **macOS playback quality.**
- **Testing** on hardware and servers we haven't touched (NVIDIA, Intel, real Linux GPUs, macOS), and the app UI on Jellyfin 10.11.

### 2.4 SyncPlay (watch together)

Wanted, so moved out of the plan's "not in v1" list. All the endpoints below are in the 12.2 OpenAPI spec and none are obsolete (checked against the dev server). Effort: **L** overall, but it splits into the steps below. Priority: **P2**.

**How Jellyfin's SyncPlay works:**
- The server keeps a group: its members, a shared play queue, and a state (idle, waiting, paused, playing).
- Clients send requests over HTTP:
  - Group: `POST /SyncPlay/New`, `Join`, `Leave`, `GET /SyncPlay/List`.
  - Playback: `Pause`, `Unpause`, `Seek`, `Stop`, `NextItem`, `PreviousItem`.
  - Queue: `SetNewQueue`, `Queue`, `SetPlaylistItem`, `RemoveFromPlaylist`, `MovePlaylistItem`, `SetRepeatMode`, `SetShuffleMode`.
  - Readiness: `Buffering`, `Ready`, `SetIgnoreWait`, `Ping`.
- The server answers through the session **websocket** (`/socket`):
  - `SyncPlayGroupUpdate` messages: joined, left, state changes, queue changes.
  - `SyncPlayCommand` messages: Unpause, Pause, Seek or Stop, each with a `When` timestamp in server time and a `PositionTicks`.
- Clients estimate the offset between their clock and the server's with `GET /GetUtcTime`, repeated a few times (NTP-style, keeping the lowest-latency sample). They then execute each command at the given moment. The web client corrects drift during playback by briefly changing the playback speed, or by skipping when the drift is large.

### Cozy look backlog

Moving every screen onto the cozy look (`docs/DESIGN.md`) that the sign-in screen started, and building it from shared components rather than page-local helpers. The approach has three parts. **C1 retints the whole app at once**: egui's `Visuals` and the old token names start pointing at the cozy palette, so every page gets the lavender colours without any layout change. **C3 pulls the widgets pages draw for themselves into `widgets/`**, so each one is restyled once rather than per page. **C4–C12 then restructure one screen at a time**, starting with the screens shaped like sign-in (panels, dialogs, menus, Settings) and ending with the browsing pages and the player, which still need design decisions. Each item follows the same steps: mock it first (the `ui-mockup` skill, both themes), write what it settles into `docs/DESIGN.md`, build it, then cover it in `ui_tests` and check a screenshot in both themes.

**The component rule, from C3 on:** views compose and widgets draw. Anything a page paints that another page could use (a row, a button, a ring, a badge, a header) lives in `widgets/`, takes plain data rather than a page's types, reads its colours from `theme::tokens_of`, names itself to AccessKit, and appears in the component gallery. A page-local drawing helper is fine only when nothing else could draw it (the seek bar, the jump bar). A screen item isn't done while it still has a private copy of something `widgets/` has.
