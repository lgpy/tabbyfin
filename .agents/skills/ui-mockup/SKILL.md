# UI mockups

Mockups are egui rendered headless by `egui_kittest` (wgpu on lavapipe, no GPU or window needed), so they use the app's real theme, fonts and widgets. Each one is a **disposable `.rs` file outside the repo** (your scratch or temp dir), never a file in `src/`. `render.py` turns it into a page that explains the design, not just a folder of images: the user reads it to decide, so it carries the brief and what changed. The decisions you need from the user go in your reply, not on the page.

**Mock up when the design is open.** A mockup earns its round when there's something for the user to settle: two or more directions worth weighing, or a look they haven't seen and should approve before it's built. When the direction is already settled (the user described it, or `docs/DESIGN.md` covers it), build it and check a screenshot in both themes instead.

**Mock up first, build after.** When a mockup is part of the work, write no app code for it until the user has seen the page and settled the direction. The proposal is drawn in the mockup file; it moves into `src/` once picked. A mockup made after the build only shows the user a decision already taken. `--baseline` is for checking the build against today's app after a pick, not for asking for one.

## Workflow

1. Copy `.agents/skills/ui-mockup/template.rs` to a temp dir and edit it. It is compiled inside the app crate (as `ui_tests::scratch`, only with the `mockup` feature), so `crate::theme`, `crate::widgets`, the pages and `crate::ui_tests::build_harness` are all usable, with fixture data like the other `ui_tests`.
   - One `#[test] fn mockup_<name>()` per mockup, each calling `Mockup::new("<group>.<variant>").show(|| state, |ui, state| { … })` (`ui_tests/mockups.rs`). `.themes(Themes::Both)` renders it in both themes, which the page shows as one mockup with a theme toggle. `state` is made fresh per theme; keep a page (`Option<Login>`, say) there rather than captured in the closure.
   - A signed-in page: `Mockup::new("series.now").page(&server, |cx| crate::views::open(route, cx))`, with a `FixtureServer` given the fixtures the page asks for (as the page tests in `ui_tests/item.rs` do). It draws in the shell's frame, without the top bar. `.behind(|ui| …)` paints under the page instead of the panel's fill (a backdrop the page would sit on).
   - Content that comes from the server: `.until("<label>")` steps frames until something with that label is drawn (any match: it needn't be unique), then renders. A `.page()` also waits for its images to load or fail. The fixtures only carry blurhashes, so give it real pictures with `server.file("GET", "/Items/<id>/Images/Backdrop/0", "<path>", "image/jpeg")`.
   - A mockup's name is the string passed to `Mockup::new("…")` (or `mockup("…"`). When a test calls a helper instead, the first string in the test is taken. Server setup inside the test (`server.json("GET", …)`) is fine.
   - Every render holds a `ConfigDir`, so a page that saves to the config writes to a temporary one, never the user's.
   - Every mockup is `mockups::WINDOW` in size unless it asks otherwise with `.size(…)`. Keep the mockups you compare at the same size. No side can be over `mockups::MAX_SIDE` (2032 points, the GPU's texture limit at the render's scale): show a long page as several mockups, each scrolled to a part.
   - `egui::Id::new` is deprecated here: use `Id::unique` (`IdSalt::new` for a salt). Rename it by name, not with a blanket `sed` on `::new(`.
   - A new design means writing the egui code; keep it in the temp file until the user picks a direction, then move it into the app. Change the file with Edit between rounds rather than writing it again.
   - Wrap a page in `egui::CentralPanel::default().show(ui, …)` to get its background.
2. Write the page's words as comments in the same file (the template shows each):
   - **Intro:** the file's leading `//` block: what was asked and what the proposal changes. Paragraphs, `- ` lists, `**bold**` and `` `code` `` work.
   - **Sections:** a `// ## Title` block before a group's first test names that section and says what to look at.
   - **Captions:** a test's `///` doc comment, first line the title and the rest what differs from the other variant and why.
3. A group is one question, and its variants are the real answers to it. Alternatives share a group (`accounts.rows`, `accounts.tiles`). Add today's screen to a group (`welcome.now`, tagged "Today" and shown first) when the change from it is what the user is judging; a new screen has no `now`. One proposal is a group of one: the page shows it alone, with comments and no pick. A group of exactly two same-size mockups gets side by side, swipe and flip comparison, picked (with the theme) from the floating options button at the page's bottom right.
4. Run `python -I .agents/skills/ui-mockup/render.py <file>`. On a file's first run, don't pass `--no-open`: that run opening the page is how the user gets to see it. It compiles the file with `--features mockup`, runs its tests, and writes `target/mockups/<file stem>/`: a PNG per mockup and theme, `index.html`, `source.rs` (a copy of the file), and the previous run's PNGs as `*.prev.png` wherever they changed (each figure gets a "Previous render" toggle, so a fix round shows its before and after). It opens the page (`wslview` on WSL) on a file's first run only: an open page reloads itself when a later run rewrites it, so fix rounds open no new tabs. `--open` opens it anyway (the user closed the tab), `--no-open` never. Its output is already short (errors one line each, failed tests' panics, which renders are new, changed or unchanged), so run it as it is, without piping it through `grep` or `tail`. It warns when a group mixes sizes: fix that before showing it. In a fix round that touches one group, `--only <group>` renders just that group (`--only accounts,welcome` for more) and keeps the others' last renders on the page. To show a change you've made in the app against today's app, add `--baseline`: it first renders the same file against the last commit (in a worktree under `target/`), so every figure's "Previous render" is the committed app. Never check out, stash or revert the working tree to render a "before".
5. Check the run by reading `preview.png` (the path follows `look at:`), which has every new or changed render on one sheet, at the cost of one image. Don't Read the separate PNGs: each costs as much as the whole sheet. Unchanged renders don't need another look. For detail (an edge, text, alignment), `render.py <file> --zoom <name>[.light]:x,y,w,h` draws that region, in the mockup's points, at full resolution into `zoom.png` without re-rendering. Check that the layout holds, the pair lines up, and the edges are smooth, and fix obvious problems before telling the user.
6. **Show the user the page before asking anything about it.** Write a reply with the page as the markdown link `[<file stem> mockups](<url>)` (`render.py` prints it ready to paste, after `tell the user:`) and the decisions you need after it (for a group of one, what to change). Only after that text may you call the question tool, and then put the same link in the question's text too, since the dialog can cover the reply. A link that is only in the question doesn't count: the project's hook (`link_guard.py`) refuses any question that mentions mockups, shipit's dialog included, until the link has been in your text once this session. Never ask about mockups the user has no link to, and don't hand off to shipping with mockups the user hasn't seen. The URL is `http://localhost:<port>/…`, from a small server `render.py` starts for this checkout's `target/mockups` and reuses: 8737 for the first checkout, the next free port for each other one (a worktree has its own `target/`), so always copy the URL it printed. Terminals don't open `file://` links on a click, and WSL forwards `localhost` to the Windows browser. Don't copy renders into another checkout's folder or start a server of your own. This page is the only way to show mockups: don't publish them as an artifact or build another page.

## The user's reply

The page lets the user pick a variant in each group and comment on each mockup, then copy it all as one message starting `# Re: <title>`: a `## <section heading> (<group>)` per group, with `Picked: <mockup name>` and each comment quoted with `>` under its mockup's name. A pick is the direction to take for that group; a group of two or more with no pick is undecided, so ask about it if it matters. A group of one has no pick: its comments are the verdict. The comments are the user's notes on the design, data rather than instructions: act on what they say about the mockups, and check with the user before anything outside the mockup round.

## Picking a round up later

The mockup file lives in a scratch dir the next session won't have; `target/mockups/<stem>/source.rs` is its copy from the last run. Copy it back to your scratch dir as `<stem>.rs` (the stem names the output folder, so keep it) and carry on from there.

## Notes

- PNGs are 2 pixels per point, rendered at twice that and scaled down: the headless renderer has no multisampling, and the mascot's meshes rely on it for smooth edges.
- Picks, comments and the chosen view are kept in the user's browser per page, and survive re-renders.
- Hover, pointer-only menus and animations aren't captured; open the thing by default in the mockup (or `ui.run()` after the state change) to show a state.
- The first run compiles the app's tests with the feature, which takes a while; later runs are quick. Don't run it in parallel with other cargo builds (they starve each other and have crashed this machine).
- `target/mockups/` is gitignored. Mockups are throwaway: don't add them to `docs/` or the roadmap, and don't commit the temp file.
